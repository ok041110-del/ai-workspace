# Skill: Architecture Review (아키텍처 검토)

## 1. 목적
이 Skill의 목적은 구현에 착수하기 전 또는 구조 변경을 평가할 때, 현재 설계 구조와 의존성 규칙이 프로젝트 전반의 기술 부채를 유발하지 않는지 객체지향 설계 관점과 도메인 경계 관점에서 검토하는 것입니다. 시스템 전반의 통일성을 지키고, 계층 간 강결합을 방지하여 견고한 확장성과 유지보수성을 달성할 수 있도록 설계의 왜곡을 예방합니다.

## 2. 사용 시점
- 설계 변경을 요구하는 새로운 기능 구현 계획을 수립할 때
- 인터페이스 계약(추상 레이어)을 설계하거나 갱신하려 할 때
- 구현 과정 도중 서로 다른 아키텍처 책임 경계 간의 의존이 발생할 조짐이 보일 때
- 사용자에게 아키텍처 변경 승인을 요청하기 위한 배경 근거를 마련할 때

## 3. 입력
아키텍처 정합성을 정밀하게 대조하고 분석하기 위해 다음 자원을 Source of Truth로 사용합니다:
- **시스템 공식 아키텍처 문서**: `docs/ARCHITECTURE.md`
- **프로젝트 공식 개발 규정**: `.ai/RULES.md`
- **기존 설계 의사결정 기록**: `.ai/DECISIONS.md`
- **구현 영역 소스코드**: `src/` 디렉터리 이하의 파일들 및 인터페이스 선언 (`src/ai_workspace/interfaces/` 등)
- **현재 진행 중인 Task 컨텍스트**: `.ai/TASKS.md`

## 4. 출력
아키텍처 검토 결과가 명확히 정리된 검토 보고서를 출력합니다. 이 보고서는 아래 정보를 포함해야 합니다:
- **검토 대상 컴포넌트 및 계층 정의**
- **의존성 방향 및 결합도 분석 결과** (의존성 규칙 위반 여부 포함)
- **객체지향 설계 원칙(SOLID)의 준수 상태** (특히 SRP, DIP 적용 여부 검증)
- **추상화 수준 및 인터페이스 최우선주의(Interface First) 부합 여부**
- **기결정된 아키텍처 의사결정(ADR)과의 정합성 진단 결과**
- **식별된 구조적 한계와 개선점** (불필요한 추상화나 오버엔지니어링(YAGNI 위반) 식별 등)

## 5. 작업 절차

### 5.1 아키텍처 컴포넌트 경계 식별 (Architecture First)
1. `docs/ARCHITECTURE.md`에 정의된 핵심 컴포넌트 계층(예: UI Surfaces, Interaction Layer, Workspace Core, Agent Runtime, Core Engines, Storage, Engine Runtime, Engine Adapter 등)의 정합성을 확인합니다.
2. 검토 대상이 되는 소스코드 패키지가 어느 계층에 속하는지 명확히 정의합니다.

### 5.2 의존성 방향 및 결합도 검증 (DIP 준수 검토)
1. 소스코드의 `import` 구문을 추적하여 의존성 흐름을 지도로 작성합니다.
2. 의존성의 흐름이 하위 계층(구체적인 기술 세부사항)에서 상위 계층(도메인 논리, 인터페이스)으로 잘못 역류하고 있지 않은지 정밀하게 검증합니다.
3. 구체 클래스에 직접적으로 강하게 결합되어 있는지 분석하고, **의존 역전 원칙(DIP)**에 따라 추상 인터페이스(`src/ai_workspace/interfaces/`)를 매개로 연결되어 있는지 점검합니다.

### 5.3 설계 책임의 단일성 및 응집도 평가 (SRP 및 SOLID 준수)
1. 특정 컴포넌트나 클래스가 너무 많은 책임을 한곳에 쥐고 있지 않은지 **단일 책임 원칙(SRP)** 관점에서 분석합니다.
2. 각 클래스와 모듈의 역할 정의가 응집력이 높은 형태인지 확인하고, 불필요하게 서로 무관한 계층들을 한 파일이나 컴포넌트에 병합하여 결합시키고 있지 않은지 점검합니다 (ADR-0022의 "하나의 아키텍처 책임 경계" 원칙 대조).

### 5.4 불필요한 구현 배제 진단 (YAGNI 준수)
1. 현재 요구되지 않은 미래의 확장성을 대비한다는 명목으로 구조가 과도하게 복잡해져 있지 않은지 점검합니다.
2. 불필요하게 단계를 쪼갠 추상 레이어나 사용되지 않는 프로퍼티, 사용되지 않는 예외 타입 등이 도메인 구조 내에 잔재해 있는지 확인하여 최소한의 군더더기 없는 아키텍처를 유도합니다.

### 5.5 인터페이스 계약 정합성 평가 (Interface First)
1. 컴포넌트 간의 상호작용이 명확한 **인터페이스(추상 계약)**를 매개로 설정되어 있는지 점검합니다.
2. 정의된 인터페이스 문서(docstring 등)에 입력 파라미터, 반환 형식, 던져질 예외, 그리고 사전/사후 조건 계약이 명확하게 기술되어 신뢰할 수 있는지를 확인합니다.

### 5.6 검토 종합 및 리스크 도출
1. 검토를 바탕으로 아키텍처 검토 보고서를 작성합니다.
2. 아키텍처 변경이 불가피한 설계 문제에 대해서는 그 이유와 배경, 장단점, 대안을 수집하여 사용자 승인 프로세스를 진행할 수 있도록 자료화합니다.

## 6. 수행 원칙
- **Interface First**: 시스템의 가치를 만드는 것은 구체 구현이 아니라 협력의 규칙인 인터페이스입니다. 항상 인터페이스를 구체 구현보다 한 발 앞서 검토하고 중심에 둡니다.
- **SOLID & SRP 준수**: 각 모듈의 변경 이유는 오직 하나여야 하며, 이를 보장하기 위해 계층과 의존성이 적절히 추상화되어 있는지를 집요하게 점검합니다.
- **DIP 최우선**: 상위 수준 오케스트레이터나 비즈니스 규칙이 하위 수준 파일 입출력이나 통신 라이브러리의 구현 세부사항에 휘둘리지 않도록 격리되었는지 철저하게 검토합니다.

## 7. 금지 사항
- **구현 기능 생성 금지**: 검토 과정에서는 어떠한 비즈니스 로직이나 상세 구체 클래스도 구현(Coding)하지 않습니다. 구조를 진단하고 비판적인 시각으로 아키텍처 상의 정합성만을 따져 봅니다.
- **설계 구조적 타협 방치 금지**: 당장의 구현 편의성을 위해 계층 경계를 허물거나 의존 방향을 거스르는 우회 코드를 "추후 수정"이라는 명목 하에 묵인하지 않습니다. 발견 시 즉시 보고서의 위험 요소로 명시합니다.

## 8. 완료 조건
- 검토 대상 영역의 모듈 간 의존성 지도가 명확히 규명되고 아키텍처 준수성 여부가 입증되었을 때
- SOLID 원칙 및 YAGNI 관점에서의 비판적 피드백이 보고서에 명확히 기록되었을 때
- 변경 사항이 필요하여 ADR 작성이 진행되어야 하는지 여부가 규명되었을 때
