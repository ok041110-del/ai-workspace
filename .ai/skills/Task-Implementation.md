# Skill: Task Implementation (작업 구현)

## 1. 목적
이 Skill의 목적은 수립된 구체적 작업 계획에 기초하여 단 하나의 특정 작업을 높은 완성도로 실제로 구현하는 것입니다. 소스 코드를 안전하게 추가 및 수정하고, 테스트를 통해 구현의 신뢰성을 보장하며, 관련된 프로젝트 상태 문서를 즉시 최신화함으로써 항상 "작동하는 상태"의 안전한 마스터 브랜치를 유지합니다.

## 2. 사용 시점
- `.ai/TASKS.md`에 등재된 `IN_PROGRESS` 상태인 단일 Task를 처리하고 실제 코드를 작성해야 할 때
- 기획된 테스트 계획에 맞춰 실질적인 단위 테스트 및 프로덕션 코드를 개발할 때
- 해당 구현 세부사항에 대한 증명을 검증하고 이를 저장소 상태에 확정하고 싶을 때

## 3. 입력
구현 단계에서 길잡이가 되는 필수적인 사실 정보원입니다:
- **수립된 계획**: 이전 단계에서 생성된 **Task 작업 계획서**
- **개발 원칙**: `.ai/RULES.md` (Surgical Changes, Simplicity First)
- **대상 소스코드 및 인터페이스**: `src/` 이하 모듈
- **대상 테스트 명세**: `tests/` 이하 파일

## 4. 출력
작업이 올바르게 완료된 후 도출되어야 하는 최종 유효 산출물입니다:
- **프로덕션 코드**: 비즈니스 요구사항을 충족하는 최소한의 안전한 소스코드
- **단위/통합 테스트 코드**: 정상, 비정상, 경계 조건 검증이 완비된 테스트 파일
- **테스트 통과 결과 보고**: 로컬 검증 도구(pytest 등) 실행 완료 터미널 출력 이력
- **문서 및 계획 상태 갱신**: `.ai/TASKS.md`에서의 Task 상태를 `DONE`으로 변경, 작업 로그 작성

## 5. 작업 절차

### 5.1 점진적 테스트 작성 (Goal-Driven Execution / TDD)
1. 구현해야 하는 동작을 나타내는 실패하는 단위 테스트(Failing Test)를 `tests/` 디렉터리에 먼저 추가합니다 (Test-Driven Development 권장).
2. 테스트에서 주입되는 파라미터가 비어 있거나 올바르지 않은 값일 때 적절한 도메인 예외가 정상적으로 발생하는지 검증하는 시나리오를 구체화합니다.

### 5.2 극도의 단순성을 지닌 프로덕션 코드 구현 (Simplicity First)
1. 오직 작성된 테스트를 통과시키는 데 집중하여 프로덕션 코드를 최소한으로 구현합니다.
2. 불필요하게 복잡한 분기, 쓰이지 않는 추상화 계층, 나중에 쓸지도 모르는 가상의 속성을 절대로 코딩하지 않습니다.
3. 코드 스타일은 PEP 8 및 프로젝트 규정(`.ai/RULES.md`의 Python 코딩 규칙)에 정렬합니다:
   - 모든 공개 함수에 명확한 타입 힌트(type hint) 명시
   - 불필요하고 당연한 설명을 늘어놓는 주석 대신 비직관적인 맥락의 'Why'만을 간략하게 기술

### 5.3 절제된 영향 범위 유지 (Surgical Changes)
1. 본 Task와 관련 없는 다른 컴포넌트의 코드를 임의로 리팩토링하거나 개선(Cleanup)하려 시도하지 않습니다.
2. 발견된 기존의 죽은 코드(Dead Code)나 레거시는 직접 지우지 않고, 분석 및 리뷰를 위해 오로지 기록으로만 보고합니다.

### 5.4 테스트 및 품질 도구 상시 검증 (Test Before Complete)
1. 로컬 가상 환경을 통하여 현재 구현한 소스 코드 및 전체 테스트 스위트를 실행합니다 (예: `poetry run pytest`).
2. 코드 품질 도구 및 정적 분석 도구(Ruff, MyPy 등)를 실행하여 단 하나의 정적 분석 에러나 경고도 용인하지 않고 완전히 클린한 상태를 만듭니다:
   - `poetry run ruff check .`
   - `poetry run mypy .`
3. 모든 테스트와 품질 가이드라인을 극복할 때까지 **[작업 -> 검증 -> 수정]**의 안전한 회로를 반복 수행합니다.

### 5.5 연관 문서의 점진적 갱신 (Documentation First)
1. 구현된 최신 기술 스펙이 기획 문서와 어긋나지 않도록 `docs/ARCHITECTURE.md` 등의 스펙 문서를 동일한 작업 영역 내에서 즉시 갱신합니다.
2. 절대 작동하지 않는 죽은 문서를 마스터 브랜치에 남겨두지 않습니다.

### 5.6 작업 상태 변경 및 이력 확정
1. `.ai/TASKS.md`로 이동하여 방금 완료한 Task의 상태를 `DONE`으로 선언합니다.
2. 진행 로그(Progress Log)에 작업 수행일, 주요 구현 내용, 특이사항, 그리고 실행 결과를 기록합니다.

## 6. 수행 원칙
- **One Task At A Time**: 절대로 두 개 이상의 작업을 융합하여 구현하지 않습니다. 이전 작업이 테스트를 통과하고 안전하게 검토를 거쳐 종료되기 전에는 다음 작업을 손대지 않습니다.
- **Surgical Changes**: 최소한의 메스로 환부만 수술하듯, 작업 범위를 벗어난 영역에는 어떠한 소소한 코드 수정의 유혹도 물리치고 극단적인 변경 격리 상태를 유지합니다.
- **Goal-Driven Verification**: 구현의 완성은 감각적인 판단이나 눈대중이 아니라 기획된 모든 단위/경계 테스트 시나리오가 100% 통과되는 수치적 사실에 의해서만 선언됩니다.

## 7. 금지 사항
- **우회적 아키텍처 타협 금지**: 임의로 `import` 방향을 왜곡하거나 인터페이스의 보증 계약을 파괴하면서 단순히 "동작만 되게" 만드는 변칙적 지름길 구현을 철저하게 금지합니다.
- **Task 범위 이탈 금지**: "하는 김에 같이"라는 발상으로 Task 명세서에 정의되지 않은 타 영역의 신규 기능 및 개선 코드를 한 커밋에 뒤섞어 추가하지 않습니다.

## 8. 완료 조건
- 수립한 작업 계획상의 모든 프로덕션 코드와 그에 매핑되는 단위 테스트 작성이 완료되었을 때
- 로컬 테스트 환경 상에서 `pytest`, `ruff`, `mypy`가 100% 성공(클린) 통과를 달성했을 때
- `.ai/TASKS.md` 및 연관 문서의 상태 전이 표기가 정확하게 동기화되었을 때
