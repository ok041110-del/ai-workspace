# Skill: Repository Analysis (저장소 분석)

## 1. 목적
이 Skill의 목적은 AI가 작업 공간에 투입되었을 때, 대상 프로젝트의 현재 상황을 정확하고 왜곡 없이 파악하는 것입니다. 프로젝트의 구조, 개발 규칙, 기합의된 설계 결정사항, 그리고 진행 상황에 대한 정확한 이해를 바탕으로 이후의 모든 작업을 신뢰할 수 있는 사실에 기반하여 수행할 수 있도록 합니다.

## 2. 사용 시점
- 새로운 개발 세션이 시작되었을 때
- 새로운 에이전트가 작업 영역에 처음 진입했거나 교체되었을 때
- 다른 에이전트로부터 작업을 인계받아 컨텍스트를 동기화해야 할 때
- 프로젝트의 현재 이정표(Milestone)와 작업(Task)의 진척도를 확인하고자 할 때

## 3. 입력
분석을 수행하기 위해 저장소 내에 존재하는 다음 자원들을 Source of Truth(진실의 원천)로 사용합니다:
- **프로젝트 루트 파일**: `README.md`, `pyproject.toml`, `.gitignore` 등
- **기본 가이드라인**: `.ai/RULES.md`
- **프로젝트 계획 및 상태**: `docs/ROADMAP.md`, `.ai/TASKS.md`
- **아키텍처 및 설계 의사결정**: `docs/ARCHITECTURE.md`, `.ai/DECISIONS.md`
- **컨텍스트 및 기억**: `.ai/MEMORY.md`
- **저장소 현재 빌드/실행 환경 및 Git 상태**

## 4. 출력
저장소 분석 결과를 정리한 구체적인 보고서를 출력합니다. 이 보고서는 아래 정보를 포함해야 합니다:
- **프로젝트 개요 및 식별된 디렉터리 구조**
- **현재 진행 중인 Milestone 및 활성 Task 식별 결과**
- **기존 테스트 환경 및 테스트 통과 상태 요약**
- **수집된 Git 상태 (수정 중인 파일 유무, 브랜치 정보 등)**
- **추가적인 구현에 직접적인 영향을 미치는 주요 제약 및 결정사항 목록**

## 5. 작업 절차

### 5.1 저장소 구조 및 기본 구성 탐색 (Repository First)
1. 저장소 루트 디렉터리의 파일 목록을 조회하여 프로젝트의 주요 파일 구조를 파악합니다.
2. `README.md`를 읽고 프로젝트의 핵심 목적, 기술 스택, 빌드 및 실행 방법을 확인합니다.
3. `pyproject.toml` 또는 이에 상응하는 패키지 설정 파일을 통해 프로젝트 의존성, 런타임 환경, 테스트 프레임워크 설정을 파악합니다.

### 5.2 프로젝트 로드맵 및 백로그 상태 분석
1. `docs/ROADMAP.md`를 열고, 전체 프로젝트의 이정표(Milestone) 상 현재 어떤 위치에 와 있는지와 과거 진행 기록을 확인합니다.
2. `.ai/TASKS.md`를 분석하여 다음 사항을 정확하게 식별합니다:
   - 현재 진행 중인 Milestone 번호와 해당 Milestone의 DoD(Definition of Done)
   - 현재 `IN_PROGRESS` 상태인 Task ID와 세부 목적
   - 다음으로 진행해야 할 `TODO` 상태의 Task 후보들
3. `.ai/MEMORY.md`를 읽어 세션 간 영속화되어야 하는 요약된 장기 메모리와 현재 세션에서 주의 깊게 유지해야 하는 비즈니스 맥락을 로드합니다.

### 5.3 아키텍처 규칙 및 기결정 사항 파악 (Source of Truth)
1. `docs/ARCHITECTURE.md`를 통해 시스템의 주요 컴포넌트 구조, 계층 간 의존성 방향, 그리고 준수해야 할 구조적 제약을 분석합니다.
2. `.ai/DECISIONS.md`를 읽고 기존에 승인된 ADR(Architecture Decision Record) 목록을 훑어보며, 아키텍처적 타협점과 그 배경을 정확하게 이해합니다.
3. `.ai/RULES.md`에 정의된 개발 및 코딩 표준, 한국어 사용 원칙, 네이밍 관례를 숙지합니다.

### 5.4 런타임 및 인프라 상태 검증
1. 현재 프로젝트가 위치한 Git 브랜치 이름과 스테이징 영역에 변경 중인 파일이 있는지 확인합니다.
2. 테스트 프레임워크 실행 명령(예: `poetry run pytest`)을 실행하여 현재 코드 베이스의 테스트 통과 여부 및 테스트 스위트 구성을 확인합니다.

### 5.5 분석 결과 요약 작성 및 보고
1. 위 단계에서 수집한 정보를 기반으로 현재 프로젝트 진행도와 동작 유효성을 종합한 분석 보고서를 작성합니다.
2. 수집된 근거 없이 모호한 영역에 대해서는 절대로 추측하여 기록하지 않고, 사실만을 있는 그대로 명시합니다.

## 6. 수행 원칙
- **Repository First**: 모든 조사와 상태 판단은 사용자의 설명에만 의존하지 않고, 항상 저장소 내의 실제 파일과 코드, Git 커밋 상태를 진실의 원천(Source of Truth)으로 삼아 수행합니다.
- **추측 배제 (No Guessing)**: 명시적으로 코드나 문서에 기록되지 않은 시스템의 작동 규칙이나 세부 요구사항을 AI가 자체적으로 추측하여 해석하지 않습니다. 판단의 근거가 모호할 경우 분석 보고서에 질문 항목으로 남겨 사용자에게 확인을 요청합니다.
- **Surgical Reading**: 비용과 문맥 오류를 줄이기 위해 작업에 직접 관련된 범위 외의 코드를 광범위하게 읽지 않고, 계층적으로 핵심 경로의 파일만을 정밀하게 읽습니다.

## 7. 금지 사항
- **코드 및 문서 수정 금지**: 저장소 분석 단계에서는 절대로 어떠한 소스 코드나 마크다운 문서도 임의로 수정, 생성, 혹은 삭제하지 않습니다. 분석은 철저하게 읽기 전용(Read-Only) 동작이어야 합니다.
- **불필요한 외부 정보 남용 금지**: 저장소 내부의 구체적인 소스코드와 기합의된 설계 의사결정을 무시하고 외부 LLM이 임의로 학습한 일반론적인 설계를 저장소 코드에 대입하여 해석하지 않습니다.

## 8. 완료 조건
- 저장소 내 모든 필수 구조 요소 및 문서(`README`, `ROADMAP`, `TASKS`, `DECISIONS`, `RULES`, `MEMORY`)의 최근 갱신 상태와 진척 경로가 명확하게 밝혀졌을 때
- 현재 진행 중인 Milestone 및 작업해야 할 특정 Task가 식별되었을 때
- 현재 프로젝트의 소스 코드 빌드 및 테스트 유효성 상태가 확인되었을 때
