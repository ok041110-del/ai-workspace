# Skill: Task Planning (작업 계획 수립)

## 1. 목적
이 Skill의 목적은 식별된 단일 작업을 구현하기 전에, 변경을 완결하기 위해 필요한 정밀한 전술 계획을 작성하는 것입니다. 작업 계획 수립을 통해 기능의 범위를 명확히 획정하고, 무분별한 코드 작성을 예방하며, 점진적이고 완벽한 변경을 수행하여 예기치 않은 부작용이나 회귀 버그(Regression)를 방지하는 안정장치를 구축합니다.

## 2. 사용 시점
- `.ai/TASKS.md` 상에서 활성화(IN_PROGRESS)할 예정이거나 활성화한 신규 Task를 시작할 때
- 해당 Task의 비즈니스 및 기술적 변경 범위와 대상을 명확히 정의하고자 할 때
- 테스트 주도 개발(TDD)을 위해 구체적인 테스트 시나리오를 선제적으로 설계할 때

## 3. 입력
실현 가능하고 완결성 높은 계획을 수립하기 위해 다음 자원을 분석합니다:
- **현재 대상 Task 명세**: `.ai/TASKS.md` 내 해당 Task 항목
- **참조할 개발 규칙**: `.ai/RULES.md` (Think Before Coding / Simplicity First)
- **현재 구현 구조 상태**: `src/` 내 관련 모듈 코드 및 `tests/` 내 기존 테스트 스위트
- **아키텍처적 제약 사항**: `docs/ARCHITECTURE.md`

## 4. 출력
다음 7개 핵심 요소를 정량적이고 구체적으로 서술한 **Task 작업 계획서**를 출력합니다:
- **목표 (Goal)**: 이 작업을 통해 궁극적으로 무엇을 달성하고자 하는가
- **구현 범위 (In-Scope)**: 수정되거나 추가되어야 하는 세부 동작 단위와 명세
- **제외 범위 (Out-of-Scope)**: 불필요한 엔지니어링과 추측을 막기 위해 이번 작업에서 철저히 제외할 범위
- **수정/추가 대상 파일**: 구체적인 파일 경로 목록
- **테스트 계획 (Test Plan)**: 정상 동작 및 경계조건/예외를 검증하기 위한 구체적인 테스트 스나리오와 실행 도구 및 방법
- **문서 영향도 (Documentation Impact)**: 어떤 제품 문서나 운영 문서를 수정해야 하는지 파악
- **예상 위험 및 대응책 (Risks & Mitigations)**: 잠재적인 부작용과 이를 회피하기 위한 대책

## 5. 작업 절차

### 5.1 요구사항 정밀 분석 및 추측 배제 (Think Before Coding)
1. 대상 Task의 명세를 완전히 독파합니다. 모호하거나 중의적인 요구사항이 존재하는 경우, 임의로 해석하여 추측하지 않고 즉시 사용자 질문 등을 통해 범위를 좁힙니다.
2. 해결해야 할 비즈니스 규칙이 기존의 도메인 계약 및 규칙에 부합하는지 비교합니다.

### 5.2 경계 획정 및 불필요한 구현 필터링 (YAGNI 준수)
1. 요청받은 동작에 한정하여 최소한으로 필요한 구현 범위(In-Scope)를 수립합니다.
2. 미래를 대비하기 위한 확장 설계나 요청에 포함되지 않은 리팩토링 항목을 과감히 제외 범위(Out-of-Scope)로 분류하여 범위를 좁힙니다.

### 5.3 변경 영향도 평가 및 파일 목록 작성 (Surgical Changes)
1. 현재 소스코드를 탐색하여 이 변경이 전파될 파일 목록과 직접 수정해야 할 파일의 세부 파일 경로를 파악합니다.
2. 불필요하게 다른 책임을 갖는 파일들로 변경이 유출되지 않는지 점검하고 극도로 절제된(Surgical) 변경 계획을 세웁니다.

### 5.4 세부 테스트 시나리오 기획 (Test Before Complete)
1. 변경이 성공했음을 완벽히 증명할 수 있는 정량적 성공 검증 시나리오를 작성합니다.
2. 예외 처리 동작, 빈 값 주입 등 극단적인 경계 조건(Edge Case)에 대한 실패 및 예외 검증 시나리오를 기획합니다.
3. 테스트를 실행할 구체적인 명령 방식(예: `poetry run pytest tests/interfaces/test_my_service.py`)을 사전에 상세하게 준비해 둡니다.

### 5.5 변경 전후 문서 갱신 영역 도출
1. 변경 사항이 도메인 계약 변경을 동반하는 경우 `docs/ARCHITECTURE.md` 또는 관련 마크다운 문서의 갱신 계획을 수립합니다.
2. 구현이 끝난 뒤 수기 또는 자동화 도구로 갱신해야 할 프로젝트 계획서(`.ai/TASKS.md`, `.ai/MEMORY.md` 등) 영역을 확인합니다.

### 5.6 계획서 작성 및 검토
1. 수립된 작업 계획서를 작성하여 저장소의 현재 맥락에 공유할 준비를 갖춥니다.
2. 구현 중 계획의 변경이 필요한 경우 계획을 점진적으로 유연하게 조정하며, 그 원인을 기록합니다.

## 6. 수행 원칙
- **Think Before Coding**: 단 한 줄의 실질 코드도 계획 수립 전에 작성하지 않습니다. 충분히 생각하고 설계를 도출하는 것이 코딩 시간을 단축시키는 유일한 길입니다.
- **YAGNI 준수 (You Aren't Gonna Need It)**: 당장 쓸모가 증명되지 않은 모든 가상의 추상 구조와 부가 기능은 계획에서 배제합니다.
- **Goal-Driven Execution**: 모든 작업은 검증 가능한 구체적인 성공 지표(테스트 스위트)가 성립되어야만 완성이 정의될 수 있습니다.

## 7. 금지 사항
- **실제 소스코드 구현 금지**: 작업 계획 단계에서는 계획 문서의 작성 이외에 실질적인 개발 로직의 코딩을 수행하지 않습니다.
- **과도하게 광범위한 변경 설정 금지**: 한 작업 범위에 다수의 컴포넌트나 연관 없는 레이어 수정을 밀어 넣어, 커밋 크기를 키우고 위험을 가중하는 계획을 절대 잡지 않습니다.

## 8. 완료 조건
- 7개 핵심 항목(목표, 구현 범위, 제외 범위, 수정 파일, 테스트 계획, 문서 영향, 위험 요소)이 명확히 명시된 계획서가 완성되었을 때
- 계획을 통해 검증하고자 하는 구체적 테스트 실행 명령어와 시나리오가 수립되었을 때
- 계획의 실행 타당성이 AI 및 사용자에 의해 명확히 검증되었을 때

> 계획서가 완성되면(위 완료 조건 충족 시) `.ai/RULES.md` §2.4 Stage
