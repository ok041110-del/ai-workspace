# Skill: Code Review (코드 리뷰)

## 1. 목적
이 Skill의 목적은 구현이 끝난 직후, 작성된 결과물이 시스템의 전반적인 품질 기준과 객체지향 설계 원칙을 만족하는지 엄격하고 비판적으로 검증하는 것입니다. 잠재적인 논리적 결함과 버그를 릴리즈 전에 완벽히 제거하고, 설계 타협점을 확인하여 기술 부채의 무분별한 유입을 사전에 엄격히 통제합니다.

## 2. 사용 시점
- 특정 Task의 구현 및 로컬 테스트 검증이 완전히 끝난 뒤, 사용자에게 최종 제출하기 전
- Pull Request(PR) 또는 병합 전 변경 내용에 대해 객관적인 검토가 필요할 때
- 기존 코드에 대해 고도화 작업이나 리팩토링 타당성을 분석하고자 할 때

## 3. 입력
철저하고 누수 없는 리뷰를 수행하기 위해 다음 요소를 Source of Truth로 상정합니다:
- **실제 소스코드의 Diff**: 변경된 프로덕션 코드 및 테스트 코드 일체
- **해당 Task의 작업 계획서**: 이전에 수립된 **Task 작업 계획서**
- **아키텍처 스펙**: `docs/ARCHITECTURE.md`
- **구현 규칙**: `.ai/RULES.md`

## 4. 출력
검출된 문제를 분류하고 건설적인 개선 방향을 동반한 **코드 리뷰 결과 보고서**를 출력합니다. 이 보고서는 아래 정보를 포함해야 합니다:
- **리뷰 개요**: 검토 대상 변경 범위 요약
- **코드 품질 진단**: 네이밍 관례(PEP 8), 불필요한 복잡성, 코드 가독성 평가
- **설계 품질 검증**: SRP, DIP 준수 및 인터페이스 계약 준수 상태
- **테스트 품질 평가**: 신규 시나리오 구성 범위 및 경계/실패 케이스 검증 정밀성 평가
- **식별된 잠재 버그 및 메모리/자원 누수 리스크**
- **구체적인 개선 권고사항**: 단순 지적이 아닌, 즉각 반영 가능한 수준의 대안 코드 가이드

## 5. 작업 절차

### 5.1 계획 대비 구현 범위 일치성 점검 (YAGNI 준수 확인)
1. 변경된 소스코드의 전체 범위가 당초 수립된 작업 계획서의 구현 범위(In-Scope)에 완전히 정렬하는지 대조합니다.
2. 제외 범위(Out-of-Scope)로 분류되었던 내용이 구현 과정에서 슬그머니 침투했거나, 불필요한 미래 예측용 클래스/메서드가 오버엔지니어링되어 추가되지 않았는지 점검합니다.

### 5.2 객체지향 설계 설계 기준 및 인터페이스 검증 (SOLID 준수 확인)
1. 수정된 클래스들이 단일한 변경 이유(SRP)만을 쥐고 있는지 검토합니다.
2. 협력하는 모듈들이 구체 구현에 직접 조인되지 않고, 명시적인 인터페이스(DIP)를 통과하여 유연하게 설계되었는지 검사합니다.
3. 아키텍처적 의존성 가이드라인(`docs/ARCHITECTURE.md`에 선언된 결합 관계)을 우회하거나 위반한 흔적이 존재하지 않는지 정밀 점검합니다.

### 5.3 테스트 완전성 및 한계 조건 검출 (Test Before Complete)
1. 작성된 단위 테스트가 단순히 커버리지만 채우기 위해 정상적인 해피 패스(Happy Path)만을 검증하고 있지 않은지 확인합니다.
2. 예외 케이스, 잘못된 값 유입, 빈 입력 등 극한의 경계 조건(Edge Case)에 대한 실패 테스트 시나리오가 얼마나 빈틈없이 마련되었는지 평가합니다.

### 5.4 코드 가독성 및 관례 점검
1. 네이밍이 Python PEP 8 및 프로젝트 관례를 위반하지 않는지(영어 식별자, 올바른 snake_case/PascalCase 사용 등) 검토합니다.
2. 불필요하고 장황한 설명성 주석(What을 명시하는 주석)을 식별자로 대체할 수 없는지 확인하고, 비직관적인 판단 배경(Why)만이 깔끔하게 주석으로 관리되었는지 확인합니다.

### 5.5 개선안 코드화 및 제안
1. 식별된 취약성이나 코드 중복, 비효율적 동작에 대해 추상적인 말장난이 아닌, 즉각 복사하여 적용할 수 있는 구체적인 개선 제안 코드 스니펫을 작성하여 보고서에 반영합니다.

## 6. 수행 원칙
- **임의 구현 금지 (No Arbitrary Changes)**: 리뷰 과정에서 발견한 문제에 대해 AI가 승인 없이 프로덕션 코드를 은근슬쩍 수정해 버리지 않습니다. 항상 리뷰 보고서에 기술하여 공식적으로 해결하는 단계를 밟도록 유도합니다.
- **Strictly Critiques**: 좋은 동료가 된다는 것은 결함을 대충 덮어두는 것이 아닙니다. 기술 품질의 타협 없는 엄격성을 통하여 최고의 견고함을 갖추도록 냉정하게 평가합니다.
- **Explain Reasoning**: 제안하는 모든 리팩토링이나 변경 권고안에는 그것이 가져올 구조적 득실, 가독성 향상 정도, 그리고 설계 대안이 명확한 이론적 근거와 함께 서술되어야 합니다.

## 7. 금지 사항
- **실제 소스코드 직접 수정 금지**: 코드 리뷰를 진행하는 단독 행동 내에서는 절대 임의로 소스코드를 직접 수정하는 행위를 병행하지 않습니다. 리뷰와 구현은 엄밀히 격격히 분리된 서로 다른 컨텍스트 체인입니다.
- **주관적 편향에 치우친 트집 금지**: 단순 취향 수준의 서식 논쟁이나 성능 향상이 증명되지 않는 무익한 추상화를 위한 논리 구조 변경을 강요하지 않습니다. 반드시 SOLID, YAGNI, SRP 등 명확하고 실질적인 원칙에만 기반합니다.

## 8. 완료 조건
- 설계 원칙(SOLID), 구현 원칙(YAGNI, Surgical Changes), 품질 규정이 모두 반영된 완전한 형식의 리뷰 보고서가 도출되었을 때
- 식별된 결함에 대한 명확한 개선 가이드 코드 스니펫이 완성되었을 때
- 검토 결과 아키텍처 정합성에 일말의 결점도 없음이 수치적으로 완전히 검증되었을 때
